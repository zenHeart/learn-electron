# 发展历史：从 Atom Shell 到今天

> **一句话本质：Electron 的十三年是一部「学着跟上 Chromium」的历史——版本节奏从随缘发版收敛到 8 周一个 major，治理从 GitHub 的内部项目成长为 OpenJS 基金会下的中立开源项目；你今天感受到的每一次升级压力，都是这段历史里某个决策的直接产物。**

读完这一篇，你会得到一张能挂在墙上的时间线，并能回答三个此前只能靠死记的问题：为什么 Electron 每 8 周就出一个大版本？为什么停在旧版本上收不到安全补丁？为什么 API 会在大版本之间废弃？

这三个问题的答案，分别是技术线、支持策略与语义化版本三段历史的产物。理解了成因，[版本策略与升级清单](/appendix/versioning)里的规则就不再是需要背诵的教条，而是常识。

## 为什么要读框架史

框架史不是八卦。一个框架的历史，是它所有「现状合理性」的来源。

Electron 尤其如此。它由三个互相咬合的部件组成（见下一篇[技术架构剖析](/part1-background/03-architecture)），其中 Chromium 自身以极高频率演进，Electron 被迫发展出一整套发版节奏与治理结构来跟上它。

这套节奏又反过来决定了你的升级节奏。看不懂这条因果链的团队，会反复踩同一类坑：把 Electron 当成「稳定不动的库」锁进项目，三年后被迫连跳二十个大版本——本章末尾的坑位警报会完整拆解这个事故剧本。

作为阅读地图，三条历史线各有下游去向：

- 技术线的版本节奏 → 决定你的升级策略（[版本策略与升级清单](/appendix/versioning)）
- 治理线的中立性 → 进入选型依据（[Electron 是什么](/part1-background/01-what-is-electron)）
- 生态线的应用谱系 → 证明这套架构的承载力（案例库与实战篇）

## 心智模型：十三年时间线

先看全景，再进细节。下表按时间正序排列，第四列是本书视角——历史上发生的每件事，最终都会落到你今天的某个日常决策上。

带着这一列读，历史才不是年表，而是因果。

| 时间 | 版本 | 大事 | 对开发者的意义 |
| --- | --- | --- | --- |
| 2013.03 | — | 仓库首个 commit；Cheng Zhao（zcbenz，GitHub 实习生）创建 Atom Shell，作为 Atom 编辑器的骨架 | node-webkit 与 CEF 之外的第三条路诞生 |
| 2014.04 | 0.x | Atom 公测；Slack、GitKraken、WebTorrent 成为早期采用者 | 「编辑器骨架」被验证可以长成通用桌面壳 |
| 2015.04 | 0.x | 更名 Electron | 摆脱「Atom 附属品」定位，成为独立项目 |
| 2016 | 1.0 | 发布 v1.0，作出 API 稳定承诺 | 生产环境可以放心上车 |
| 2017 | 1.x | 早期 Chromium 集成库 brightray 完成使命，并入主仓库 | 架构收敛，为后续提速铺路 |
| 2018 | 2.0 | 引入语义化版本（SemVer） | 依赖变更可预期，破坏性变更有了预告机制 |
| 2019 | 6.0 | 改为 12 周一个大版本，对齐 Chromium；同年治理变革（工作组模型 + OpenJS 基金会） | 升级从「偶发事件」变成「例行公事」 |
| 2020 | 10.x | 官方 Discord 社区上线 | 求助与跟进有了固定渠道 |
| 2021 | 12+ | Chromium 提速至 4 周后，Electron 跟进为 8 周节奏；中国用户组成立（cnpm 镜像支持） | 升级窗口进一步收紧 |
| 2026 | 44.x | 每 8 周一个 major，官方维护最新三条版本线 | 单个版本的安全更新窗口约 24 周 |

这张表里有三条独立演进的线索，下面三节分别展开：

- **技术线**：版本节奏如何被 Chromium「绑架」，又如何主动绑死
- **治理线**：一个公司内部项目如何交给社区
- **生态线**：一个编辑器骨架如何变成万能壳

三条线在 2019 年交汇——那一年 Electron 同时改了发版节奏和治理结构，从此「跟上 Chromium」从理想变成了制度。

这张表也是一张决策工具，三个典型用法：

- **新项目选版本**：直接上最新稳定 major（或次新），让支持窗口最大化——不要为了「稳」选旧版，旧版只是更早过期的内核
- **老项目算死线**：找到你当前版本的所在行，往下一行就是它的替任者，替任者发布约 8 周后你的版本掉出支持线——把这个日期写进迭代计划
- **排查兼容性问题**：先定位你版本行的内核组合（对应关系在[技术架构剖析](/part1-background/03-architecture)），再拿组合去搜已知问题——「Electron 22 + macOS 14」比「Electron 白屏」是好得多的搜索词

## 技术线：从随缘发版到锁死 Chromium 节奏

### 2013：第三条路

2013 年想做「Web 技术的桌面应用」，市面上只有两条成熟路线：

- **node-webkit**（后来的 NW.js）：把 Node 能力直接带进网页，集成方式激进
- **CEF**（Chromium Embedded Framework）：把 Chromium 打包成给 C++ 程序用的嵌入库，要求你自己写宿主程序

两条路线都活着，但都带着先天约束：前者把系统的钥匙直接交给网页（安全模型的根源问题），后者要求你有 C++ 宿主团队。

同年 3 月，GitHub 实习生 Cheng Zhao 为正在开发的 Atom 编辑器造了第三个轮子：Atom Shell。它的杀手特性是**把完整的 Node.js 和完整的 Chromium 装进同一个运行时**——用 Web 技术画界面，用 Node 调系统能力，两者在同一个可执行文件里。

2014 年 4 月 Atom 公测，Slack、GitKraken、WebTorrent 迅速跟进。人们发现这个「编辑器骨架」装什么应用都行——它从 Atom 的附属品，开始走向通用桌面运行时。

### 2016–2018：给生产环境吃的两颗定心丸

早期 Electron 版本号在 0.x 徘徊，API 随时可能变，没人敢把正经产品押上去。转折点是两个承诺：

- **2016 年 v1.0**：官方承诺核心 API 稳定。「1.0」不是功能里程碑，而是信用里程碑——它告诉生产团队：API 不会明天就翻脸
- **2018 年 v2.0**：引入语义化版本。从此 major 升级意味着可能有破坏性变更，minor/patch 语义清晰，依赖管理与 CI 锁版本都有了可推理的规则

### 2019–2021：主动绑上 Chromium 的战车

真正的心态转变发生在 v6（2019 年）：Electron 把发版节奏改为**每 12 周一个 major，与 Chromium 的发布周期对齐**。

在此之前，「用上最新版 Chromium」是 nice-to-have；在此之后，它成了优先级。跟不上的代价是双重的：旧 Chromium 背着已知安全漏洞，且在新操作系统上的行为没人验证。

2021 年 Chromium 把自己的节奏提速到 4 周一版，Electron 随即跟进到 **8 周一个 major**，并保持至今。

这不是 Electron 自己想发这么快，而是它的部件在跑，它必须跟上。理解这一点，就理解了升级压力的来源：**压力不是 Electron 给你的，是 Chromium 给 Electron、再传导给你的**。

### 怎么读 Electron 的版本号

节奏讲完了，落地到你自己项目的 `package.json` 里那串数字：

```text
44.2.0
│ │ └── patch：bug 修复与安全补丁（含 Chromium / Node 的安全回移）
│ └──── minor：新功能、新 API，向后兼容
└────── major：可能有破坏性变更——Chromium 和 Node 大版本同时更换
```

两个实用读法：

- **判断一个版本还活多久**：官方同时维护最新三个 major。以 8 周一个 major 计算，44 发布后，42 / 43 / 44 是支持线，41 在下一个 major 发布时退役——一个版本的官方寿命约 24 周
- **判断一次升级的量级**：跨 major 看升级公告的 breaking changes 清单（Chromium 侧 + Node 侧）；major 内的 minor / patch 升级可以放心跟进，这正是例行升级策略的依据

还有第三个读法：**判断你缺的东西在哪个版本**。想要某个 Chromium 特性或某个 Node 特性，先查 [Electron Releases 对照表](https://releases.electronjs.org/) 确认它随哪个 major 进来；每个版本的完整变更（含 Chromium / Node 升级明细）在 [GitHub 的 releases 页](https://github.com/electron/electron/releases)——这是升级公告的一手来源，比任何二手教程都可靠。

各版本精确的发布与退役日期，以[版本支持时间线](https://www.electronjs.org/docs/latest/tutorial/electron-timelines)官方页为准。

## 治理线：从公司项目到中立资产（2019）

前六年，Electron 本质上是 GitHub 的内部项目：核心团队在 GitHub，决策在 GitHub，路线图跟着 Atom 的需求走。

2019 年发生了两件事，把它变成了一份中立资产：

1. **工作组（WG）治理模型**：项目按职能拆分为八个工作组，各自的职责与权限公开成文。贡献者不再需要「进核心团队」才能影响项目——想推动发版改进就参与 Releases 组，关心安全策略就参与 Security 组
2. **所有权移交 OpenJS 基金会**：项目的中立家从 GitHub 变成基金会。GitHub（及其母公司 Microsoft）如今只是众多贡献方之一——不少原核心团队成员现在在 Microsoft 工作，但他们是贡献者群体的一部分，而不是项目的所有者

八个工作组各自守一块阵地：

| 工作组 | 管什么 |
| --- | --- |
| Releases | 发版流程与发布质量 |
| Upgrades | 跟随 Chromium / Node 的升级工作 |
| API | API 设计、评审与废弃流程 |
| Security | 安全策略与漏洞响应 |
| Ecosystem | 官方周边工具链（脚手架、调试器等生态工具） |
| Outreach | 对外布道、文档与内容 |
| Community | 社区渠道运营（Discord、用户组等） |
| Infrastructure | 构建与 CI 基础设施（编译集群等） |

对开发者的意义很实际：**你不依赖任何一家公司的战略心情**。一家公司可以砍掉不赚钱的产品线，但一个有八个工作组、几十名外部贡献者、基金会托管的项目，不会因为一次组织调整而停摆。

选型时「项目会不会死」这个问题的答案，就写在治理结构里。

## 生态线：从编辑器骨架到万能壳

### 应用谱系的扩张

生态的扩张路径值得一看，因为它证明了这套架构的通用性：

- 编辑器起步：Atom，以及后来最成功的门面 VS Code
- 通信客户端：Slack、Discord——长期驻留、多团队、语音视频的重客户端形态
- 开发工具：GitKraken、Postman
- 设计工具：Figma 桌面版——对渲染性能要求极高的实时协作负载
- 知识与安全类：Notion、Obsidian、1Password——本地数据与系统级集成为核心诉求

这些应用的共同点是「长期驻留、深度系统集成、界面复杂多变」，正好压在 Electron 三个部件的舒适区上。本站的[应用 Hub](/hub/apps) 收录了更完整的名单，可以按类别翻阅。

为什么大厂敢把十年的产品押上去？答案恰好是前两条线的交集：v1.0 的 API 稳定承诺与 SemVer 让升级成本可预期，2019 年的治理变革让项目存续不依赖任何一家公司的战略——一个是技术信用，一个是组织信用，两者共同构成「敢押注」的前提。

### 社区与基础设施

2020 年官方 Discord 上线，2021 年中国用户组成立，cnpm 提供镜像分发支持——国内开发者 `npm install electron` 不再需要跨国拉 200MB 二进制，镜像的具体配置见[安装指南](https://www.electronjs.org/docs/latest/tutorial/installation)。

对一个需要频繁升级的框架来说，社区渠道本身就是生产力：升级踩坑时，Discord 和用户组里大概率有人先踩过。

### 工程文化：机器撑起的 8 周节奏

8 周发一个 major（还不算中间的 patch 和安全补丁），人肉流程撑不住。官方 10 周年博客披露的自动化基建，值得每个需要发版的团队看看人家做到了什么程度：

| 工具 | 职责 | 撑住的环节 |
| --- | --- | --- |
| Not Goma | 分布式编译集群，全量构建从小时级压到分钟级 | 8 周节奏的物理前提 |
| CFA | npm 发布流程的 2FA 自动化 | 发布的安全与效率兼得 |
| Sheriff | 仓库权限自动化管理 | 大规模贡献者的权限治理 |
| Sudowoodo（bot） | 自动化发布 | 每个版本按点发车 |
| Trop（bot） | 把安全补丁 backport 到仍在支持的老版本线 | 老版本线的安全更新 |
| Roller（bot） | 依赖滚动升级 | 依赖不腐化 |

这套体系的启示：**可持续的快节奏不是靠人加班，而是把节奏里的每个环节都机器化**。

当你抱怨每 8 周要升一次级时，记住对方为了让你「升得动」在另一头做了多少自动化——安全补丁会由 Trop 自动回移到三条支持线，你升到的每一个 patch 都是白捡的加固。

::: exp
**版本节奏如何换算成你的升级决策。**官方支持政策是「只维护最新三个 major 版本」。以 8 周一个 major 计算：一个版本从发布到掉出支持线，寿命约 24 周（五个半月）。

掉出支持线的版本，**收不到任何安全补丁**——Chromium 的高危漏洞修复只落在三条支持线内。由此推出三条实战纪律：

1. **把升级例行化**：每 1–2 个 major 跟进一次（8–16 周一次），单次跨度小、回归范围可控。最忌「攒三年，一次跳二十个」
2. **锁版本前先算账**：查[版本支持时间线](https://www.electronjs.org/docs/latest/tutorial/electron-timelines)，算清楚你锁的版本的 EOL 日期，写进项目风险清单
3. **留在支持线内是白赚的**：安全修复由 Trop 自动 backport 到三条线，停在支持线内的每个 patch 升级都是零成本加固

完整操作清单见[版本策略与升级清单](/appendix/versioning)。
:::

::: pitfall
**把 Electron 当「稳定不动的库」，是最贵的认知错误。**事故剧本高度雷同：立项时锁定某个 major，「功能够用」就再也不升。

两三年后，某次安全审计、某个新操作系统版本或某块新硬件逼你升级，此时面对的是连跳二十多个大版本的迁移：Node 大版本跨越导致所有原生模块 ABI 变化要重编；默认安全策略早已改变——`nodeIntegration` 从默认开到默认关就是历史版本里真实发生过的变更；一路废弃的 API 需要逐个改写。工作量远超「每半年轻松升一次」的累计。

还有一层暗坑：**操作系统在动，而旧 Chromium 从未在新系统上被验证过**。Apple Silicon 上跑老版本 Electron 的崩溃问题（见[案例库 · Apple Silicon 崩溃](/cases/06-apple-silicon)）就是典型——不是你的代码坏了，是你带的那个旧浏览器不认识新硬件。

记住：Electron 的「稳定」指 API 层面的语义化版本承诺，从来不是「这个库不动」。正确姿势是把「每半年跟进一次 major」写进团队日历，与依赖安全扫描同级对待。
:::
