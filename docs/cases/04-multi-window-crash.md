# 案例 4：多窗口关闭崩溃与一次真实的版本升级决策

> 本案例前半是一个具体崩溃，后半展示「什么情况下该升级 Electron、升级要做什么」——把一次生产升级决策完整摊开。

## 现象

多窗口应用（主窗口 + 多个子窗口）在**关闭子窗口时崩溃率偏高**，集中在特定主版本线上。同时该版本线逐渐暴露：Chromium 漏洞不再收到修复、新系统版本兼容性问题出现。

## 诊断与决策

崩溃归因：旧版 Electron 在多窗口销毁时序上有已知缺陷（特定版本线的 regression），社区在后续版本修复。评估了三条路：

1. 留在旧版本，自己规避（约束窗口关闭顺序、延迟销毁）——治标，规避代码本身脆弱；
2. 小版本内升级——不含修复，无效；
3. **跨大版本升级**——含修复 + 安全更新 + 新特性，但要付完整迁移成本。

## 升级决策框架

升级动机要写成可核对的清单（三类动机对应不同紧迫度）：

| 动机 | 紧迫度 | 例 |
|---|---|---|
| 安全：Chromium 漏洞停止修复 | 高 | 旧支持线 EOL |
| 稳定：特定版本已知 bug（本例） | 高 | 关闭子窗口崩溃 |
| 功能：新 API / 新系统兼容 | 中 | UtilityProcess、新版系统通知规范 |

## 工作项分解（来自一次真实跨 3 个大版本升级）

| 工作项 | 说明 |
|---|---|
| 废弃 API 迁移（主进程） | 逐条核对 [breaking changes](https://www.electronjs.org/docs/latest/breaking-changes)，grep 全仓扫描废弃符号 |
| preload / 渲染层迁移 | `contextIsolation` 默认值变化、`ipcRenderer` 用法收紧 |
| `remote` 体系移除 | `@electron/remote` 依赖的替代方案（IPC 封装，见[IPC 章节](/part2-core/09-ipc)工具箱） |
| 原生 SDK 配套 | ABI 变化 → SDK 重编 + 全量回归（见[原生章节](/part4-advanced/25-sdk-integration)） |
| 配套 SDK 对齐 | 加速/音视频等外部 SDK 的兼容版本确认 |
| 构建链与签名回归 | 打包产物、签名链、更新通道全链路验证 |
| 灰度与回滚预案 | 按渠道灰度 + 崩溃率看板盯盘 + 一键回退开关 |

**教训型经验**：升级窗口期双 DSN 分流监控（新旧版本各一个监控 project），升级后崩溃率对比才有可信基线；多窗口崩溃类问题，升级后要用自动化脚本批量「开 N 窗-关 N 窗」循环压测，人工点不出来。

## 预防

- 把「Electron 版本支持线状态」纳入季度技术债盘点（EOL 前主动规划，而不是被安全事件逼着升级）。
- 升级 checklist 固化到仓库模板（[版本策略附录](/appendix/versioning) 有完整清单）。
- 无法升级的存量客户端，用「远程规则引擎 + 崩溃联动回滚」兜底（见[性能章节](/part3-engineering/18-performance)）。
